# 0001: The first state of jrs-upgrade is an extraction of jrsctl's upgrade subsystem

**Context.** jrsctl v2.3.0 is the final release of the all-in-one tool; it is being split into four applications, and jrs-hotfix (the first) was rebuilt lean from the start. The upgrade subsystem cannot be rebuilt that way in one step: its plan reaches the doctor, the full export, the engine, the SQLite journal, buildomatic and service control, so a dependency closure from `ops.upgrade` and the upgrade command touches 326 of jrsctl's 365 source files. The customer who triggered the split (the NGRA 8.2 to 10.1 guide of 2026-10-01) needs working upgrade tooling before the slimming can be designed against real runs.

**Decision.** The first push is an extraction baseline: jrsctl's upgrade code and everything it needs, copied into one Maven module under `com.jaspersoft.jrsupgrade`, renamed, with the hotfix subsystem cut, building green with its unit tests. Slimming and the twelve seeded issues follow as changes against working code.

What was copied: all of `core`, all of `jrs`, all of `ops` except the hotfix package, and the `app` commands an upgrade needs end to end (`init`, `doctor`, `smoke`, `upgrade` with `rollback` and `--test`, `customizations`, `export`, `import`, `runs`, `config`, `secrets`, `selfcheck`, `docs`, `home`, the guided menu, `--json` and its schemas), the unit tests of all of that, and the test fixtures. `export` and `import` stay as commands, not only as operations, because the upgrade plan takes the full export and the rollback re-imports it, and their tests seed the runs the `runs` tests need.

What was cut:

- `ops.hotfix` (31 classes) except `HotfixPaths` and `HotfixException`, two home-path helpers the upgrade and customization code share; renaming them is a follow-up.
- Hotfix re-application during an upgrade: `HotfixReconciler`, `RepackHotfixBundle`, `EmbeddedStep`, `BundleZips`, `ReconcileSteps.PlanHotfixReapply`, the `--reapply-hotfixes` flag and the `reapplyHotfixes` option, the hotfix factory in `UpgradeRuntime` and `PlanRegistry`. The hotfix ledger belongs to jrs-hotfix; jrsctl's `hotfix_installed` table is never written by this tool. Reading jrs-hotfix's ledger during reconcile is a new issue, not a port of the old step.
- The `hotfix` and `keys` commands, the hotfix manifest schema and the hotfix and keys JSON output schemas, the hotfix authoring guide, the `dist` module (jlink image, signing) and the `acceptance` module (phase tests against the shaded jar). The signing-key package `core.keys` and the publisher key resource stay for now because `RunService` references them; both go with the first slimming change.
- The state store keeps its hotfix tables and migrations: the schema is versioned and shared with homes written by jrsctl, and the `home set` refusal on an installed hotfix still protects such a home.

Renaming, applied mechanically: `com.jaspersoft.jrsctl` to `com.jaspersoft.jrsupgrade`; `JRSCTL_` to `JRS_UPGRADE_`; `Jrsctl` to `JrsUpgrade` in class names (four files renamed); `jrsctl` followed by an identifier character to `jrsupgrade`; any other `jrsctl` to `jrs-upgrade` (the command name, the YAML file, the system properties); `jrsctl-version.properties` to `jrs-upgrade-version.properties`. Hand fixes the rules needed: a local variable and two test method names that the last rule had turned into `jrs-upgrade(`; two test underlines whose length followed the old name; the lower-case home variable in a withheld-names test, which must carry the new prefix; the adapter service-loader test, which now shares a classpath with the app tests' own factory; the idempotency coverage guard, which looked for the jrs tests in a sibling module.

**Consequences.** The tool works today exactly as jrsctl's `upgrade` did, under the new name, on the same single-hop paths, on Tomcat, outside containers. The code carries jrsctl's weight: SQLite, REST, secrets, the full menu. Each slimming step (flatten the packages, replace the journal, decide on REST, trim the menu, port the acceptance harness, add the release workflow, rewrite the inherited docs) is its own issue and its own reviewable change. 1,522 unit tests pass at the extraction; the Jacoco floor is set just under the measured coverage and rises as the slimming lands. Commits are not pushed until the maintainer has read the design document (`docs/superpowers/specs/2026-10-01-jrs-upgrade-design.md` in jrsctl) and this record.
