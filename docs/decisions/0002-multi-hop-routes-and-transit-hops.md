# 0002: Multi-hop upgrades run as one plan with transit hops that deploy nothing

**Context.** The compatibility matrix lists single-hop pairs only. For an 8.2.0 server and a 10.1.0 target the planner refused, although the matrix already holds the two hops the vendor documents (8.2 to 10.0 newdb, 10.0 to 10.1 samedb), and the NGRA guide (section 4) works the route out by hand (issue #1). Running the hops as separate upgrades would start the server on 10.0, need a Tomcat certified for it, and leave a rollback point on an intermediate version.

**Decision.**

- The matrix lists the GA `releases` a route may stop at. When no single path covers a pair, `CompatMatrix.route` returns the route with the fewest hops; among equal lengths, the one with the latest stops wins. The first hop runs in `--mode` and every later hop runs samedb, because a newdb hop rebuilds the database from an export and only the running server's export (point B) exists. A pair a single path covers is never routed. A pair offered only in the other mode is refused as before (exit 6, naming the mode).
- The operator passes one unpacked package per hop with a repeated `--package`. Packages are matched to hops by the version each states, and the last hop may take the first `--package` when it states none. A missing package is refused with exit 2, naming the route and the `--package` arguments it needs. A package that matches no hop is refused with exit 1.
- The route runs as one plan with one point B. The service is stopped once. Every hop but the last is a **transit hop**: its properties and keystore file are staged into its own package and its vendor script runs against the repository database. It deploys nothing, and nothing starts on its version. Its step ids carry `@<version>`, and its markers and backups live in `runs/<runId>/transit-<version>/`, so the journal never confuses two hops. A failure in any hop compensates back to point B. A rollback never lands on an intermediate version.
- `vendor-upgrade.started` is appended to, not overwritten. Its first line names the first script of the route. When that script is newdb, `upgrade rollback --restore-database` rebuilds the old database from the point-B export, and the manifest's `mode` is that first hop's mode.
- The rehearsal (`--test`) runs the vendor's validation for every hop.

**The ambiguity, and the safer option.** The vendor documents no way to run `js-upgrade-*` "without deploying". The NGRA guide runs buildomatic from a migration host with `appServerType=skipAppServerCheck`, the vendor's setting for a buildomatic with no application server. Whether every target's upgrade path still copies a webapp under that setting is not documented. A transit hop therefore stages both `appServerType=skipAppServerCheck` and `appServerDir` pointing at a scratch directory under the jrs-upgrade home (`transit/<version>/tomcat`), never the live Tomcat. If buildomatic deploys anyway, it deploys there. The transit vendor step's postcheck also fails the run, and so compensates to point B, when the live webapp afterwards states the transit version. Neither guard depends on how buildomatic interprets the setting.

**Consequences.** A transit hop needs no Tomcat certified for its version, so `verify-target-package` skips that check for it. It does need a JDK the hop's version accepts, and each hop's `verify-target-package` judges `vendor.javaHome` against its own version. The 8.2 to 10.1 route needs Java 17. The scratch directory is left under the home after the run, because it holds nothing a later run reads. The acceptance runs against real 10.0 and 10.1 packages still have to confirm the first guard; until then the second one stands behind it.
